🗄️ Modelo de datos · Cloud Firestore

¿Cómo guarda todo la base de datos?

Firestore organiza los datos en colecciones (como tablas) de documentos (como filas). No hay JOINs — el agente y la app leen cada colección por separado. Las flechas → indican referencias entre colecciones.

🎰 bets → 👤 users · uid
🎰 bets → 📊 odds · matchId
👤 users → 👥 groups · groupId
🤝 joinRequests → users + groups
🃏 figuritasAlbums → 👥 groups · groupId
🔮 predictions → 👤 users · uid
☁️ Backend gestionado · Google Firebase

Sin servidor propio — Firebase hace el trabajo

No hay ningún servidor Express, FastAPI ni proceso propio corriendo 24/7. Firebase actúa como backend completo: la app escribe y lee directamente desde el navegador con el SDK. Las reglas de seguridad de Firestore actúan como el "guard" — controlan quién puede leer/escribir qué sin código de servidor.

🤖 Agente automático · GitHub Actions cron

El único "servidor" — y vive solo ~10 segundos

Un script Node.js que GitHub Actions ejecutaba cada 5 minutos vía cron durante el Mundial. No hay ningún servidor permanente: GitHub prende una VM, corre el script, la VM desaparece. Costo fijo: cero. Cron desactivado desde que terminó el torneo (19-jul-2026) — el trabajo de fondo ya no tiene partidos que trackear, así que ahora solo corre manualmente (workflow_dispatch) para no seguir gastando lecturas/escrituras de Firestore sin necesidad.

⚛️ Interfaz de usuario · React 18 + Babel Standalone · Sin proceso de build

Frontend: JSX compilado en el browser, sin npm ni webpack

No hay paso de build. Los archivos .jsx se transpilan en tiempo real por Babel Standalone cargado desde CDN. React 18 también viene de CDN. Cualquier editor de texto es suficiente para contribuir. El viewport al cargar determina qué componente raíz se monta: App (móvil <1024px) o AppWeb (escritorio ≥1024px).
